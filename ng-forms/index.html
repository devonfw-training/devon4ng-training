Custom Validation Interface

            
              interface ValidatorFn {
                (c: AbstractControl): {
                  [key: string]: any;
                } | null;
              }

ValidatorFn takes an AbstractControl to validate.

Returns null if valid.

Returns {[key: string]: any} as error definition.

Custom Validation Example

Higher order function can return ValidatorFn

which returns { forbiddenName: name } as error.

            
              function forbiddenName(forbiddenName: string): ValidatorFn {
                return (control: AbstractControl): ValidationErrors => {
                  const name = control.value;
                  const isForbidden = forbiddenName === name;
                  return isForbidden ? { forbiddenName: name } : null;
                };
              }

    Adding custom validators to Template Driven forms via Directives

    <input type="text" name="first" ngModel noForbiddenName>
    1. Create directive with matching selector - e.g. 'noForbiddenName'
    2. Extend NG_VALIDATORS dependency via providers property (directive meta data)
    3. Implement validate() for directive and call validator - e.g. forbiddenNameValidator

    Directive Validator example

                
              @Directive({
                selector: '[noForbiddenName][ngModel],[noForbiddenName][formControl],[noForbiddenName][formControlName]',
                providers: [{ 
                  provide: NG_VALIDATORS, 
                  useExisting: forwardRef(() => ForbiddenNameValidator), 
                  multi: true 
                }]
              })
              export class ForbiddenNameValidator implements Validator {
                
                validator = forbiddenNameValidatorFn;
                
                validate(c: FormControl) {
                  return this.validator(c);
                }
              }

    Custom Form Fields - Why Talk About This?

    • Manual wiring - works once
    • Breaks when reused elsewhere
    • Own interface = everyone has to learn it
    • Reusable = same interface as native fields
    - manual wiring: track value yourself, emit changes yourself - works, but only in the one place you built it for - reused in a different form -> breaks down, pattern doesn't carry over - could invent your own interface instead of Angular's - but then every other dev has to learn YOUR interface instead of the standard one - reusable custom field needs to speak the same interface as Angular's native fields (input, select, ...) - for Signal Forms that interface is FormValueControl / FormCheckboxControl, not ControlValueAccessor - see next slides - second half of reusability, beyond the interface: don't bake decisions into the field's implementation (e.g. which format is valid, which values are allowed, when to switch segments) - forward those decision factors as inputs and let the using component decide. Field stays generic, host decides the specifics.

    Custom Validators Live in the Schema

    Before building a custom field, note where a custom validator lives: in the schema, not in the field. A plain native <input> already gets custom validation:

                
              loginForm = form(this.loginModel, (path) => {
                // custom rule: return an error object, or null when valid
                validate(path.website, ({ value }) => {
                  return value().startsWith('https://')
                    ? null
                    : { kind: 'https', message: 'URL must start with https://' };
                });
              });
            
          
    <input [formField]="loginForm.website" />

    The field (native here) does nothing - the schema owns the rule. Error shape is always { kind, message? }; all rules run, no short-circuit.

    - validate(path, ctx => error | null) is the custom-rule primitive; siblings are validateTree() (subtree / cross-field), validateHttp() (async, drives pending()), validateStandardSchema() (Zod/Valibot) - ctx also carries valueOf()/stateOf()/fieldTreeOf() to reach other fields - that's how cross-field rules work (next slide) - key teaching point: this is identical whether [formField] sits on a native input or a custom component - the control never validates

    Reusable & Cross-field Custom Rules

    Wrap validate() in a function - now it's used like a built-in:

                
              function requireHttpsUrl(path: SchemaPath<string>, opts?: { message?: string }) {
                validate(path, ({ value }) =>
                  value().startsWith('https://')
                    ? null
                    : { kind: 'httpsUrl', message: opts?.message ?? 'Use https://' });
              }

              form(this.model, (path) => requireHttpsUrl(path.website));

    Cross-field rules read another field via valueOf() - and re-run reactively:

                
              validate(path.confirmPassword, ({ value, valueOf }) =>
                value() === valueOf(path.password)
                  ? null
                  : { kind: 'passwordMismatch', message: 'Passwords do not match' });

    Conditional? Gate a rule with the when option, or groups of rules with applyWhen().

    Backup - same point, Model Driven (Reactive) flavour.

    Reusable & Cross-field - Reactive

    A ValidatorFn is already reusable - attach it to any control; cross-field = a validator on the FormGroup:

                
              // reusable custom validator - a plain ValidatorFn, drop it on any control
              function requireHttpsUrl(c: AbstractControl): ValidationErrors | null {
                return c.value?.startsWith('https://') ? null : { httpsUrl: true };
              }

              // cross-field: validate the group, not a single control
              function rangeOrder(g: AbstractControl): ValidationErrors | null {
                const { from, to } = g.value;
                return isBefore(from, to) ? null : { rangeOrder: true };
              }

              new FormGroup({
                website: new FormControl('', [requireHttpsUrl]),
                slot: new FormGroup(
                  { from: new FormControl(''), to: new FormControl('') },
                  { validators: [rangeOrder] },
                ),
              });
            
          
    <input formControlName="website">

    Backup - same point, Template Driven flavour.

    Reusable & Cross-field - Template Driven

    One NG_VALIDATORS directive = a reusable custom validator; the same pattern on an ngModelGroup gives cross-field:

                
              @Directive({
                selector: '[requireHttpsUrl]',
                providers: [{ provide: NG_VALIDATORS, useExisting: RequireHttpsUrl, multi: true }],
              })
              export class RequireHttpsUrl implements Validator {
                validate(c: AbstractControl): ValidationErrors | null {
                  return c.value?.startsWith('https://') ? null : { httpsUrl: true };
                }
              }

              @Directive({
                selector: '[rangeOrder]',
                providers: [{ provide: NG_VALIDATORS, useExisting: RangeOrder, multi: true }],
              })
              export class RangeOrder implements Validator {
                validate(g: AbstractControl): ValidationErrors | null {
                  const { from, to } = g.value;
                  return isBefore(from, to) ? null : { rangeOrder: true };
                }
              }
            
          
                
              <input name="website" ngModel requireHttpsUrl>

              <div ngModelGroup="slot" rangeOrder>
                <input name="from" ngModel>
                <input name="to" ngModel>
              </div>

    Native Controls: Wired Up by a Function

    When [formField] sits on a real <input> / <select> / <textarea>, Signal Forms calls this internally:

              
            export function nativeControlCreate(
              host: ControlDirectiveHost,
              parent: FormField<unknown>,
            ): () => void {
              // ... reads/writes the DOM element's value ...
              host.listenToDom('input', () => parser.setRawValue(undefined));
              host.listenToDom('blur', () => parent.state().markAsTouched());

              parent.registerAsBinding();
              return () => { /* keep the DOM in sync on every field update */ };
            }

    No code of yours runs here - this bridge ships with Angular for every native form element.

    - Source: @angular/forms/signals/src/directive/control_native.ts, function nativeControlCreate - Simplified: the real implementation also handles value parsing, min/max, <select> option tracking, etc. - Key line for this topic: host.listenToDom('blur', () => parent.state().markAsTouched())

    What a Native Field Already Gives You

    Custom Control Interfaces: CVA vs Signal Forms

    Form Type Custom Control Interface Available Since
    Template Driven ControlValueAccessor (CVA) Angular 2
    Model Driven (Reactive) ControlValueAccessor (CVA) Angular 2

    Signal Forms does not reuse CVA - [formField] detects these new interfaces directly, no NG_VALUE_ACCESSOR / forwardRef required.

    The Model Driven and Template Driven rows share one interface - ControlValueAccessor - so the CVA take on each topic lives as a backup slide ↓ beneath the matching Signal Driven slide.

    One Directive, Several Wirings

    [formField] is a single directive matched by attribute selector - it decides at runtime what it's sitting on:

                
              @Directive({ selector: '[formField]', exportAs: 'formField' })
              export class FormField<T> {
                readonly field = input.required<Field<T>>({ alias: 'formField' });

                ɵngControlCreate(host: ControlDirectiveHost): void {
                  if (this.controlValueAccessor) {
                    this.ɵngControlUpdate = cvaControlCreate(host, this); // reactive-forms interop
                  } else if (host.customControl) {
                    this.ɵngControlUpdate = customControlCreate(host, this);
                  } else if (this.elementIsNativeFormElement) {
                    this.ɵngControlUpdate = nativeControlCreate(host, this);
                  }
                }
              }

    Same directive, same [formField] binding - only the wiring function underneath changes.

    - Source: @angular/forms/signals/src/directive/form_field.ts, method FormField.ɵngControlCreate - host.customControl checks whether the host component has a 'value' or 'checked' model signal, i.e. implements FormValueControl/FormCheckboxControl - otherwise it falls back to the native branch - ɵngControlCreate is an internal lifecycle hook, renamed/simplified here for clarity - not meant to be called by app code - next slide: the CVA equivalent of this same dispatch decision

    Backup - same point, CVA flavour.

    One Directive, Several Wirings

    Several directives can match the same formControlName/ngModel - Angular picks exactly one value accessor:

                
              function selectValueAccessor(dir, accessors) {
                if (customAccessor) return customAccessor;   // your CVA component
                if (builtinAccessor) return builtinAccessor; // Checkbox/Select/Number/...
                return defaultAccessor;                      // plain <input>
              }

    Same idea as host.customControl - custom wins, then the closest built-in match, then the plain default.

    - built-in accessors (Checkbox/Select/SelectMultiple/Number/Range/Radio) match narrower selectors, e.g. input[type=checkbox]; DefaultValueAccessor is the catch-all fallback - a custom CVA component registers via NG_VALUE_ACCESSOR and always wins if present - same effect as host.customControl winning on the Signal Forms slide - this precedence (custom > builtin > default) is unchanged since Angular 2 - nothing version-specific to worry about here - source: @angular/forms/src/directives/shared.ts, function selectValueAccessor

    The Signal Forms Control Interfaces

                
              interface FormValueControl<T> {
                value: ModelSignal<T>;        // required
                touched?: InputSignal<boolean>; // read touched back, e.g. for styling
                touch?: OutputRef<void>;        // report a blur, marks the field touched
                disabled?: InputSignal<boolean>;
                invalid?: InputSignal<boolean>;
                errors?: InputSignal<readonly ValidationError[]>;
                // ... more optional state, see FormUiControl
              }

              interface FormCheckboxControl {
                checked: ModelSignal<boolean>;  // required - mutually exclusive with 'value'
                // ... same optional FormUiControl state as above
              }

    [formField] auto-detects which interface your component implements - no forwardRef, no NG_VALUE_ACCESSOR provider required.

    Angular Internals: The ControlValueAccessor Interface

                
              interface ControlValueAccessor {
                // model -> view: write a new value into the DOM element
                writeValue(obj: any): void;

                // view -> model: register the callback to call on input
                registerOnChange(fn: any): void;

                // register the callback to call on blur ("touched")
                registerOnTouched(fn: any): void;

                // enable/disable the DOM element
                setDisabledState?(isDisabled: boolean): void;
              }

    Source: @angular/forms - control_value_accessor.ts

    DefaultValueAccessor: How <input> Connects

    writeValue & Registering Callbacks

                
              // DefaultValueAccessor
              writeValue(value: any): void {
                const normalizedValue = value == null ? '' : value;
                this.setProperty('value', normalizedValue); // model -> view
              }

              _handleInput(value: any): void {
                this.onChange(value); // view -> model
              }
            
          
                
              // BaseControlValueAccessor
              registerOnChange(fn: (_: any) => {}): void { this.onChange = fn; }
              registerOnTouched(fn: () => void): void { this.onTouched = fn; }

    This exact writeValue / registerOnChange pattern is what CVA-based custom fields need to implement.

    Custom Field + Custom Validators

    The field is built - now wire it to validation. Two running examples:

    • app-rating-input - a single FormValueControl<number>: shows how config & constraints flow into the control
    • app-time-range-picker - a composite: shows internal (parse) vs external (schema) validation

    One rule runs through all of it: the control displays validation, the schema performs it.

    Division of Labour: Schema Validates, Control Displays

                
              // schema owns the rule
              feedbackForm = form(this.model, (path) => {
                min(path.rating, 1, { message: 'Please select a rating' });
              });
            
          
                
              // the control holds NO validation
              export class RatingInput implements FormValueControl<number> {
                value = model(0);
                touch = output<void>();
                maxStars = input(5);
              }
            
          
                
              <app-rating-input [formField]="feedbackForm.rating" />
              @if (feedbackForm.rating().touched() && feedbackForm.rating().invalid()) {
                <p>{{ feedbackForm.rating().errors()[0].message }}</p>
              }

    Anti-pattern: an isValid() inside the control. Define rules in the schema; let the control render the result.

    - companion point (previously its own "Config & Constraints Flow Into the Control" slide): besides errors()/invalid() state, two things flow INTO the control, from two different places: - channel 1: maxStars - the control's OWN config input (how many stars to render), passed directly by the host - the "host decides the specifics, field stays generic" narrative from the Why slide - channel 2: [formField] also forwards the schema's constraint VALUES (min/max/required/minLength/maxLength/pattern) down to the control; the control reads them only to enhance the UI (e.g. dim stars below min, mirror to HTML5 attrs), it never runs them to validate - e.g. host template: <app-rating-input [maxStars]="10" [formField]="feedbackForm.rating" /> and in the control: maxStars = input(5); min = input<number>(); - we deliberately keep only min(path.rating, 1) in the schema here - an extra max(..., 10) would be redundant for a star rating (you can't click an 11th star when only 10 are drawn) and the duplicate 10 made maxStars and max look like the same knob - the error channel is one-directional: form -> control. The control's only way to push an error up is a parse error - covered on the error-channel slide

    Backup - same point, CVA flavour.

    Division of Labour - CVA

    Under CVA a self-validating control registers NG_VALIDATORS and contributes to its own errors - idiomatic, Angular Material does it:

                
              @Directive({
                providers: [{ provide: NG_VALIDATORS, useExisting: RatingInput, multi: true }],
              })
              class RatingInput implements ControlValueAccessor, Validator {
                validate(c: AbstractControl) { return c.value >= 1 ? null : { min: true }; }
              }

    Signal Forms has no NG_VALIDATORS equivalent - see the error-channel slide.

    Backup - CVA flavour: both sides validate.

    CVA: Host Validators Stack On Top of Internal Ones

    The host can add its own validators - they run in addition to the control's internal ones:

                
              // reactive: control self-validates (min 1) + host adds more
              new FormControl('', [Validators.required, maxRating(10)]);
            
          
                
              <!-- template-driven: extra validator directives on the same element -->
              <app-rating-input name="rating" ngModel required maxRating></app-rating-input>
    • NG_VALIDATORS is a multi-provider - Angular composes all of them
    • control.errors is the merged result (collision = same error key wins/overwrites)
    • Add-only: the host can add but not remove the control's baked-in validators

    This two-sided validation is exactly what Signal Forms drops - there the control contributes no validators (bar parse errors); all of it lives in the schema.

    Internal vs External Validation

    app-time-range-picker = two time-pickers. Each kind of check has a home:

              
            // INTERNAL (time-picker): parsing hh:mm am/pm - the ONE thing a control owns.
            // An unparseable raw value becomes a parse error via transformedValue:
            protected readonly rawValue = transformedValue(this.value, {
              parse: (raw) => isValidClock(raw)
                ? { value: raw }
                : { error: { kind: 'parse', message: 'Use hh:mm am/pm' } },
              format: (val) => val ?? '',
            });
          
        
              
            // EXTERNAL (schema): from < to is a relationship, not a parse - lives in the schema
            validateTree(path.slot, (ctx) => {
              const { from, to } = ctx.value();
              return isBefore(from, to)
                ? null
                : { kind: 'rangeOrder', message: 'Start must be before end',
                    fieldTree: ctx.fieldTree.to };
            });

    Parse = can this value even exist? Validation = is this value allowed? The rating has no parse step - a click is always a valid star.

    The Error Channel Is One-Directional

    form → control (inputs)control → form (out)
    errors(), invalid() - to displayvalue (model)
    touched, disabled, required/min/max/...touch (output, on blur)
    parse errors via transformedValue

    A control's only way to push an error up is a parse error. There is no Signal Forms equivalent of CVA's NG_VALIDATORS.

    The rating has no parse step → zero upward channel → 100% of its validation must live in the schema.

    - errors / invalid are input() signals - the form pushes them down for the control to render - this is THE structural reason a general validation rule can't live inside the component: it literally cannot reach the field's errors() - the rating makes the point sharpest: no parse => no upward error at all => everything is schema

    Reusable Field = Companion Schema

    Don't make every host re-write from < to, and don't bury it in the component. Ship a companion schema with the field:

              
            // shipped alongside the control
            export const timeRangeSchema = schema<TimeRange>((path) => {
              validateTree(path, (ctx) => {
                const { from, to } = ctx.value();
                return isBefore(from, to)
                  ? null
                  : { kind: 'rangeOrder', message: 'Start must be before end',
                      fieldTree: ctx.fieldTree.to };
              });
            });
          
        
              
            // any host - one line for the intrinsic rule, then compose its own
            meetingForm = form(this.model, (path) => {
              apply(path.slot, timeRangeSchema);                       // from < to
              min(path.slot.from, '09:00', { message: 'Opens at 9' }); // business rule
              max(path.slot.to,   '17:00', { message: 'Closes at 5' });
            });

    Rule authored once, lives in the schema layer, parent stays honest, host rules compose via apply().

    Was Co-locating Validation Ever an Anti-pattern?

    CVASignal Forms
    Self-validating controlNG_VALIDATORS - idiomaticno equivalent; errors is an input
    Upward error channelfull validator contributionparse errors only
    Home for a rulecontrol or schemaschema (control displays)
    Verdictnot an anti-patternco-locating rules → discouraged

    Why it shifted: a CVA composite was a black box (parent saw that it was invalid, not why). A Signal field tree is transparent - schema rules aggregate into form().invalid(), attach to a fieldTree, and re-run via valueOf().

    - concrete failure if you bake from<to into the component: it can't reach form().invalid(), so the form reports valid with a backwards range and the submit gate lets it through - that is the real anti-pattern - the parse exception stays in the control because a parse failure genuinely is the control's private knowledge

    Custom Field Validation - Takeaways

    • The schema validates; the control displays.
    • The only error a control owns is a parse error (transformedValue → {error}). A click-based field like the rating has none → 100% schema.
    • Config & constraints flow into the control (rating maxStars); host decides specifics, field stays generic.
    • Reusable intrinsic rules travel with the field as a companion schema + apply() - not inside the component.
    • CVA self-validation was fine; under Signal Forms it's discouraged because the error channel is form → control only.

    • Signal Forms are the current standard:
      • form model declared in code, reactivity via Signals
      • automatic two-way binding & type-safe field access
      • custom fields implement FormValueControl / FormCheckboxControl - no CVA needed
