Custom Validation Interface

            
              interface ValidatorFn {
                (c: AbstractControl): {
                  [key: string]: any;
                } | null;
              }

ValidatorFn takes an AbstractControl to validate.

Returns null if valid.

Returns {[key: string]: any} as error definition.

Custom Validation Example

Higher order function can return ValidatorFn

which returns { forbiddenName: name } as error.

            
              function forbiddenName(forbiddenName: string): ValidatorFn {
                return (control: AbstractControl): ValidationErrors => {
                  const name = control.value;
                  const isForbidden = forbiddenName === name;
                  return isForbidden ? { forbiddenName: name } : null;
                };
              }

ngModel / ngModelGroup

<input name=first ngModel>

creates property inside forms data model with key 'first'

<input name=first [ngModel]="varName">

creates one-way binding - binds a default value

                
                  
                  <input name=first [(ngModel)]="varName">
                  <input name=first [ngModel]="varName" (ngModelChange)="varName=$event">

<div ngModelGroup=group></div>

creates nested object called group inside forms data model (form.value)

    Adding custom validators to Template Driven forms via Directives

    <input type="text" name="first" ngModel noForbiddenName>
    1. Create directive with matching selector - e.g. 'noForbiddenName'
    2. Extend NG_VALIDATORS dependency via providers property (directive meta data)
    3. Implement validate() for directive and call validator - e.g. forbiddenNameValidator

    Directive Validator example

                
              @Directive({
                selector: '[noForbiddenName][ngModel],[noForbiddenName][formControl],[noForbiddenName][formControlName]',
                providers: [{ 
                  provide: NG_VALIDATORS, 
                  useExisting: forwardRef(() => ForbiddenNameValidator), 
                  multi: true 
                }]
              })
              export class ForbiddenNameValidator implements Validator {
                
                validator = forbiddenNameValidatorFn;
                
                validate(c: FormControl) {
                  return this.validator(c);
                }
              }

    Signal Forms

    Angular 21: manage form state by building on the reactive foundation of signals.

    • Automatic two-way binding
    • Type-safe field access
    • Centralized schema-based validation

    Form Model

    Create one signal that holds the data model

    If required, add validation for fields centrally at this place instead of on each and every form control

              
            interface LoginData {
              email: string;
              password: string;
            }

            @Component({
              ...
              imports: [FormField],
            })
            export class App {
              loginModel = signal<LoginData>({
                email: '',
                password: '',
              });

              loginForm = form(this.loginModel);

              onSubmit(event: Event) {
                event.preventDefault();
                // Perform login logic here
                // e.g., await this.authService.login(credentials);
              }
            }

    Binding to input fields

              
            <input type="email" [formField]="formFieldTree.email" />
            <input type="password" [formField]="formFieldTree.password" />

    Validation & Field State

    Validation rules live in a schema function passed to form()

              
            loginForm = form(this.loginModel, (path) => {
              required(path.email, { message: 'Email is required' });
              email(path.email, { message: 'Enter a valid email address' });
            });

    Every field exposes its state as signals - call it as a function:

              
            <input type="email" [formField]="loginForm.email" />
            @if (loginForm.email().touched() && loginForm.email().invalid()) {
              <span class="error">{{ loginForm.email().errors()[0].message }}</span>
            }
    • valid() / invalid() / errors() - validation state
    • touched() / dirty() - interaction state

    Custom Form Fields - Why Talk About This?

    • Manual wiring - works once
    • Breaks when reused elsewhere
    • Own interface = everyone has to learn it
    • Reusable = same interface as native fields
    - manual wiring: track value yourself, emit changes yourself - works, but only in the one place you built it for - reused in a different form -> breaks down, pattern doesn't carry over - could invent your own interface instead of Angular's - but then every other dev has to learn YOUR interface instead of the standard one - reusable custom field needs to speak the same interface as Angular's native fields (input, select, ...) - for Signal Forms that interface is FormValueControl / FormCheckboxControl, not ControlValueAccessor - see next slides - second half of reusability, beyond the interface: don't bake decisions into the field's implementation (e.g. which format is valid, which values are allowed, when to switch segments) - forward those decision factors as inputs and let the using component decide. Field stays generic, host decides the specifics.

    Native Controls: Wired Up by a Function

    When [formField] sits on a real <input> / <select> / <textarea>, Signal Forms calls this internally:

              
            // @angular/forms/signals - control_native.ts (simplified)
            export function nativeControlCreate(
              host: ControlDirectiveHost,
              parent: FormField<unknown>,
            ): () => void {
              // ... reads/writes the DOM element's value ...
              host.listenToDom('input', () => /* sync value into the field */);
              host.listenToDom('blur', () => parent.state().markAsTouched());

              parent.registerAsBinding();
              return () => { /* keep the DOM in sync on every field update */ };
            }

    No code of yours runs here - this bridge ships with Angular for every native form element.

    - Source: @angular/forms/signals/src/directive/control_native.ts, function nativeControlCreate - Simplified: the real implementation also handles value parsing, min/max, <select> option tracking, etc. - Key line for this topic: host.listenToDom('blur', () => parent.state().markAsTouched())

    One Directive, Several Wirings

    [formField] is a single directive matched by attribute selector - it decides at runtime what it's sitting on:

              
            // @angular/forms/signals - form_field.ts (simplified)
            @Directive({ selector: '[formField]', exportAs: 'formField' })
            export class FormField<T> {
              readonly field = input.required<Field<T>>({ alias: 'formField' });

              ɵngControlCreate(host: ControlDirectiveHost): void {
                if (host.customControl) {
                  this.ɵngControlUpdate = customControlCreate(host, this);
                } else if (this.elementIsNativeFormElement) {
                  this.ɵngControlUpdate = nativeControlCreate(host, this);
                }
                // (+ a ControlValueAccessor branch for Reactive Forms interop)
              }
            }
    • host.customControl - is this element a component implementing FormValueControl / FormCheckboxControl?
    • otherwise, is it a native input / select / textarea?

    Same directive, same [formField] binding - only the wiring function underneath changes.

    - Source: @angular/forms/signals/src/directive/form_field.ts, method FormField.ɵngControlCreate - ɵngControlCreate is an internal lifecycle hook, renamed/simplified here for clarity - not meant to be called by app code - This is the moment that decides: native bridge (previous slide) vs custom control (next slide)

    Native vs Custom: Who Sets touched()?

    Both paths end up calling the exact same method on the field:

    loginForm.email().touched()

    native - not your code

                    
                  // control_native.ts
                  host.listenToDom('blur', () =>
                    parent.state().markAsTouched());

                  // field/state.ts
                  private selfTouched = signal(false);
                  markAsTouched() {
                    this.selfTouched.set(true);
                  }

    custom - everything you write

                    
                  export class EmailInput implements FormValueControl<string> {
                    value = model('');
                    touch = output<void>();
                    // template: (blur)="touch.emit()"
                  }
                  // [formField]="loginForm.email"

    touched() always lives on the field, never on the control - the only thing a custom control owns is the touch output that reports the blur.

    - Common misconception: expecting a "touched output" on the custom control - there isn't one, only touch (write) and an optional touched input (read-back, see next slide) - control_custom.ts mirrors this: host.listenToCustomControlOutput('touch', () => parent.state().markAsTouched()) - touched() itself is a computed signal on FieldNodeState, shared by native and custom controls alike

    Custom Control Interfaces: CVA vs Signal Forms

    Form Type Custom Control Interface
    Template Driven ControlValueAccessor (CVA)
    Model Driven (Reactive) ControlValueAccessor (CVA)
    Signal Driven FormValueControl / FormCheckboxControl

    Signal Forms does not reuse CVA - [formField] detects these new interfaces directly, no NG_VALUE_ACCESSOR / forwardRef required.

    Ask the room: who is still building forms with Model Driven (Reactive) forms today? If most/all participants are already on Signal Forms, you can skip diving down into the CVA backup slides in the next two sections and just stay on the top row.

    The Signal Forms Control Interfaces

                
              interface FormValueControl<T> {
                value: ModelSignal<T>;        // required
                touched?: InputSignal<boolean>; // read touched back, e.g. for styling
                touch?: OutputRef<void>;        // report a blur, marks the field touched
                disabled?: InputSignal<boolean>;
                invalid?: InputSignal<boolean>;
                errors?: InputSignal<readonly ValidationError[]>;
                // ... more optional state, see FormUiControl
              }

              interface FormCheckboxControl {
                checked: ModelSignal<boolean>;  // required - mutually exclusive with 'value'
                // ... same optional FormUiControl state as above
              }

    [formField] auto-detects which interface your component implements - no forwardRef, no NG_VALUE_ACCESSOR provider required.

    Angular Internals: The ControlValueAccessor Interface

                
              interface ControlValueAccessor {
                // model -> view: write a new value into the DOM element
                writeValue(obj: any): void;

                // view -> model: register the callback to call on input
                registerOnChange(fn: any): void;

                // register the callback to call on blur ("touched")
                registerOnTouched(fn: any): void;

                // enable/disable the DOM element
                setDisabledState?(isDisabled: boolean): void;
              }

    Source: @angular/forms - control_value_accessor.ts

    Building a Custom Field

                
              @Component({
                selector: 'app-email-input',
                template: `
                  <input type="text" [value]="value()"
                    (input)="value.set($any($event.target).value)" />
                `,
              })
              export class EmailInput implements FormValueControl<string> {
                value = model('');
              }

    Used exactly like a native field - same [formField] binding as before:

                
              <app-email-input [formField]="loginForm.email" />

    DefaultValueAccessor: How <input> Connects

                
              @Directive({
                selector:
                  'input:not([type=checkbox])[formControlName],
                   input:not([type=checkbox])[formControl],
                   input:not([type=checkbox])[ngModel], ...',
                host: {
                  '(input)': '_handleInput($any($event.target).value)',
                  '(blur)': 'onTouched()',
                },
                providers: [DEFAULT_VALUE_ACCESSOR],
              })
              export class DefaultValueAccessor extends BaseControlValueAccessor
                implements ControlValueAccessor { ... }
    • Matches every native input / textarea bound via ngModel / formControl / formControlName
    • Typing fires the DOM input event - handled here, not by your component

    writeValue & Registering Callbacks

                
              // DefaultValueAccessor
              writeValue(value: any): void {
                const normalizedValue = value == null ? '' : value;
                this.setProperty('value', normalizedValue); // model -> view
              }

              _handleInput(value: any): void {
                this.onChange(value); // view -> model
              }
            
          
                
              // BaseControlValueAccessor
              registerOnChange(fn: (_: any) => {}): void { this.onChange = fn; }
              registerOnTouched(fn: () => void): void { this.onTouched = fn; }

    This exact writeValue / registerOnChange pattern is what CVA-based custom fields need to implement.
