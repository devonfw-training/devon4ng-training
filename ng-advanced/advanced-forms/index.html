Angular Form Types

Template-driven Forms Reactive Forms Signal Forms
Form model Implicit (template) Explicit (component) Explicit (component)
Data flow Asynchronous, two-way binding Synchronous, explicit binding Synchronous, explicit binding
Status Legacy - backup ↓ Legacy - backup ↓ Current standard

All three approaches keep an underlying form model - they differ in where it's declared and how the view and model stay in sync, not in whether a model exists at all.

The Reactive Forms and Template-driven Forms take on each topic lives as a backup slide ↓ beneath the matching Signal Forms slide.

- historical order: Template-driven -> Reactive -> Signal Forms - signal forms new standard: Reactive was the standard until recently - "standard" = default choice, not mandatory: depends on the project's Angular version - trade-offs: know the trade-offs of each type, not just the newest one - legacy code: everyone still needs to understand all three - legacy code exists in the wild - compatibility: Signal Forms interops with Reactive/Template-driven Forms; most teams today still mainly use Reactive - plan: mostly present Signal Forms; Reactive Forms backups sit directly below, Template-driven Forms below that Grounds the whole deck's structure: the three form types arrived in this order - Template-driven Forms, then Reactive Forms, then Signal Forms - and all three keep the same underlying form model, differing only in where it's declared and how view/model stay in sync. Signal Forms is "standard" as in the default pick for new or updatable work, not a mandate to rewrite what already exists. **Additional speaker information** Template-driven Forms' main selling point as the oldest approach: simple forms can sometimes be written more directly in the template with less boilerplate, which is also why it's worth recognizing even where it isn't your default. Adopting Signal Forms needs at least Angular 21 (experimental) or Angular 22 (stable) - this also gets restated on the later "Signal Forms - Overview" slide, flagging in case that becomes redundant. Of the two legacy flavors, Reactive Forms is covered first in the backup stacks since it's still the one most commonly found in real projects today; Template-driven Forms follows beneath it as the least relevant going forward.

Angular Form Types - Detailed Comparison

Template-driven Forms Reactive Forms Signal Forms
Form model HTML template Defined in a component Defined in a component
Data model Unstructured Structured Structured (typed)
Predictability Asynchronous Synchronous Synchronous
Form validation Directives Functions Schema functions
Mutability Mutable Immutable Signals (set / update)

Reactive Forms treat the form model as immutable - a change like setValue replaces the value rather than mutating it in place. Signal Forms keeps that same snapshot semantics, just exposed through signals instead of an AbstractControl tree.

Backup companion: the fuller side-by-side comparison from the legacy deck (form model, data model, predictability, validation style, mutability), extended with a Signal Forms column. Legacy "when to use" guidance, Template-driven Forms vs Reactive Forms: - Template-driven Forms: the template is the source of truth; suited to simple forms (e.g. login / sign-up); two-way binding; harder to test; doesn't scale well - reach for it only when the forms and their logic are simple. - Reactive Forms: the form model is the source of truth; more scalable, reusable and testable; synchronous and immutable. - Signal Forms keeps the model-as-source-of-truth and synchronous predictability, now expressed through signals.

Custom Form Fields

Custom Form Fields - Why Talk About This?

  • Manual wiring - works once
  • Breaks when reused elsewhere
  • Own interface = everyone has to learn it
  • Reusable = same interface as native fields
Frames the whole custom-fields discussion: manual wiring works once but doesn't scale, which is why a reusable field must speak Angular's own control interface instead of inventing a new one. - manual wiring: track value yourself, emit changes yourself - works, but only in the one place you built it for - reused in a different form -> breaks down, pattern doesn't carry over - could invent your own interface instead of Angular's - but then every other dev has to learn YOUR interface instead of the standard one - reusable custom field needs to speak the same interface as Angular's native fields (input, select, ...) - for Signal Forms that interface is FormValueControl / FormCheckboxControl, not ControlValueAccessor - see next slides - second half of reusability, beyond the interface: don't bake decisions into the field's implementation (e.g. which format is valid, which values are allowed, when to switch segments) - forward those decision factors as inputs and let the using component decide. Field stays generic, host decides the specifics.

Custom Validators with native Fields

Custom Validators Live in the Schema

A plain native <input> already gets custom validation:

            
              loginForm = form(this.loginModel, (path) => {
                // custom rule: return an error object, or null when valid
                validate(path.website, ({ value }) => {
                  return value().startsWith('https://')
                    ? null
                    : { kind: 'https', message: 'URL must start with https://' };
                });
              });
            
          
<input [formField]="loginForm.website" />

The field (native here) does nothing - the schema owns the rule. Error shape is always { kind, message? }; all rules run, no short-circuit.

Establishes the baseline rule before discussing custom fields at all: custom validation always lives in the schema, even for a plain native input with no custom component involved. - validate(path, ctx => error | null) is the custom-rule primitive; siblings are validateTree() (subtree / cross-field), validateHttp() (async, drives pending()), validateStandardSchema() (Zod/Valibot) - ctx also carries valueOf()/stateOf()/fieldTreeOf() to reach other fields - that's how cross-field rules work (next slide) - key teaching point: this is identical whether [formField] sits on a native input or a custom component - the control never validates

Reusable & Cross-field Custom Rules

Wrap validate() in a function - now it's used like a built-in:

            
              function requireHttpsUrl(path: SchemaPath<string>, opts?: { message?: string }) {
                validate(path, ({ value }) =>
                  value().startsWith('https://')
                    ? null
                    : { kind: 'httpsUrl', message: opts?.message ?? 'Use https://' });
              }

              form(this.model, (path) => requireHttpsUrl(path.website));

Cross-field rules read another field via valueOf() - and re-run reactively:

            
              validate(path.confirmPassword, ({ value, valueOf }) =>
                value() === valueOf(path.password)
                  ? null
                  : { kind: 'passwordMismatch', message: 'Passwords do not match' });

Conditional? Gate a rule with the when option, or groups of rules with applyWhen().

Shows wrapping validate() in a function makes a rule reusable like a built-in, and that cross-field checks are just another validate() reading a sibling field via valueOf() - not a separate mechanism.

Reusable & Cross-field - Reactive Forms

A ValidatorFn is already reusable - attach it to any control; cross-field = a validator on the FormGroup:

            
              // reusable custom validator - a plain ValidatorFn, drop it on any control
              function requireHttpsUrl(c: AbstractControl): ValidationErrors | null {
                return c.value?.startsWith('https://') ? null : { httpsUrl: true };
              }

              // cross-field: validate the group, not a single control
              function rangeOrder(g: AbstractControl): ValidationErrors | null {
                const { from, to } = g.value;
                return isBefore(from, to) ? null : { rangeOrder: true };
              }

              new FormGroup({
                website: new FormControl('', [requireHttpsUrl]),
                slot: new FormGroup(
                  { from: new FormControl(''), to: new FormControl('') },
                  { validators: [rangeOrder] },
                ),
              });

                selector: '[requireHttpsUrl]',

                  const { from, to } = g.value;

              }

One Directive, Several Wirings

[formField] is a single directive matched by attribute selector - it decides at runtime what it's sitting on:

            
              <input type="email" [formField]="loginForm.email" />
              <input type="password" [formField]="loginForm.password" />
            
          
            
              @Directive({ selector: '[formField]', exportAs: 'formField' })
              export class FormField<T> {
                readonly field = input.required<Field<T>>({ alias: 'formField' });

                ɵngControlCreate(host: ControlDirectiveHost): void {
                  if (this.controlValueAccessor) {
                    this.ɵngControlUpdate = cvaControlCreate(host, this); // reactive-forms interop
                  } else if (host.customControl) {
                    this.ɵngControlUpdate = customControlCreate(host, this);
                  } else if (this.elementIsNativeFormElement) {
                    this.ɵngControlUpdate = nativeControlCreate(host, this);
                  }
                }
              }

Same directive, same [formField] binding - only the wiring function underneath changes.

Shows [formField] is one directive that inspects its host at runtime to pick the right wiring function - why the same binding syntax works unchanged on native inputs and custom components alike. - Source: @angular/forms/signals/src/directive/form_field.ts, method FormField.ɵngControlCreate - host.customControl checks whether the host component has a 'value' or 'checked' model signal, i.e. implements FormValueControl/FormCheckboxControl - otherwise it falls back to the native branch - ɵngControlCreate is an internal lifecycle hook, renamed/simplified here for clarity - not meant to be called by app code - next slide: the CVA equivalent of this same dispatch decision

One Directive, Several Wirings

Several directives can match the same formControlName/ngModel - Angular picks exactly one value accessor:

            
              function selectValueAccessor(dir, accessors) {
                if (customAccessor) return customAccessor;   // your CVA component
                if (builtinAccessor) return builtinAccessor; // Checkbox/Select/Number/...
                return defaultAccessor;                      // plain <input>
              }

Same idea as host.customControl - custom wins, then the closest built-in match, then the plain default.

Backup companion: the equivalent selection logic Angular has always used to pick one CVA among several matching directives - 'custom beats built-in beats default' predates Signal Forms. - built-in accessors (Checkbox/Select/SelectMultiple/Number/Range/Radio) match narrower selectors, e.g. input[type=checkbox]; DefaultValueAccessor is the catch-all fallback - a custom CVA component registers via NG_VALUE_ACCESSOR and always wins if present - same effect as host.customControl winning on the Signal Forms slide - this precedence (custom > builtin > default) is unchanged since Angular 2 - nothing version-specific to worry about here - source: @angular/forms/src/directives/shared.ts, function selectValueAccessor

Native Controls: Wired Up by a Function

              host: ControlDirectiveHost,
              parent: FormField<unknown>,

              // ... reads/writes the DOM element's value ...
              host.listenToDom('input', () => parser.setRawValue(undefined));

              parent.registerAsBinding();

Division of Labour - CVA

Under CVA a self-validating control registers NG_VALIDATORS and contributes to its own errors - idiomatic, Angular Material does it:

            
              @Directive({
                providers: [{ provide: NG_VALIDATORS, useExisting: RatingInput, multi: true }],
              })
              class RatingInput implements ControlValueAccessor, Validator {
                validate(c: AbstractControl) { return c.value >= 1 ? null : { min: true }; }
              }

Signal Forms has no NG_VALIDATORS equivalent - see the error-channel slide.

Backup companion: under CVA a self-validating control registering NG_VALIDATORS is idiomatic (Angular Material does it) - the opposite stance from the Signal Forms slide above.

Backup - CVA flavour: both sides validate.

CVA: Host Validators Stack On Top of Internal Ones

The host can add its own validators - they run in addition to the control's internal ones:

            
              // reactive: control self-validates (min 1) + host adds more
              new FormControl('', [Validators.required, maxRating(10)]);
            
          
            
              <!-- template-driven: extra validator directives on the same element -->
              <app-rating-input name="rating" ngModel required maxRating></app-rating-input>
  • NG_VALIDATORS is a multi-provider - Angular composes all of them
  • control.errors is the merged result (collision = same error key wins/overwrites)
  • Add-only: the host can add but not remove the control's baked-in validators

This two-sided validation is exactly what Signal Forms drops - there the control contributes no validators (bar parse errors); all of it lives in the schema.

Backup companion: shows a host can stack its own validators on top of a control's internal ones - a two-sided model Signal Forms drops in favor of the schema owning all rules. Re-validation caveat: this stacking only works because WorkingHours/maxRating are registered as NG_VALIDATORS on the control that's actually part of the parent form tree. If a validator instead lives only inside a child's own internal FormGroup (nested one level deeper, not exposed via NG_VALIDATORS on the component itself), it won't participate in the parent form's validity or submission state - for it to count towards the parent form's validation, it must sit on the top-level control the parent can see, not buried inside the child.

                  validate(path.time, ({ value }) => {

              @Component({
                selector: 'app-time-range-picker',
                viewProviders: [{ provide: ControlContainer, useExisting: FormGroupDirective }],
                template: `
                  <ng-container formGroupName="slot">
                    <app-time-picker formControlName="from" />
                    <app-time-picker formControlName="to" />
                  </ng-container>
                `,
              })
              export class TimeRangePickerComponent implements OnInit {
                // inject parent in the constructor (this.form = parent)
                constructor(private form: FormGroupDirective) {}

                ngOnInit() {
                  // build the form structure in this component (this.form.form.addControl) -
                  // the host never has to know "slot" has a from/to shape
                  this.form.form.addControl('slot', new FormGroup({
                    from: new FormControl(''),
                    to: new FormControl(''),
                  }));
                }
              }
            
          
            
              <!-- host owns the root FormGroup only - "slot" is the picker's own business -->
              <form [formGroup]="meetingForm">
                <app-time-range-picker />
              </form>

viewProviders instead of providers: providers cannot reach up to the parent. No CVA, no composite value - just template reuse.

Same From/To UI and outcome - but TimeRangePickerComponent owns neither a value nor a FormGroup. It writes straight into the parent's form instead. Same technique as the legacy general-info exercise (now in the Exercises section): inject the parent FormGroupDirective in the constructor, addControl its own structure into it, bind via formGroupName/formControlName - just applied directly to the time-range-picker instead of taught abstractly on a generic address field. CVA-only: a Signal Forms composite just binds its children to slices of its own value() - a plain two-way-bindable signal, no ambient form-sharing mechanism needed at all - whereas CVA has no such plain model object and must reach for either a nested FormGroup or this ControlContainer trick. How the sharing actually works: formGroupName/formControlName look up ControlContainer with @Host(), which is restricted to the component's own view, so by default they can't see an ancestor component's FormGroupDirective. The constructor param FormGroupDirective is not @Host()-restricted, so DI walks past the component boundary and injects the real ancestor instance from the host's <form [formGroup]>. viewProviders then re-publishes that same instance as ControlContainer for this component's own view, so formGroupName="slot" inside resolves to it too. Because it's the same object and not a copy, this.form.form.addControl(...) mutates the host's own meetingForm directly - the host's FormGroup starts without a "slot" control at all (e.g. just { room: new FormControl('') }) until the picker adds it. Pro/con vs. the nested-FormGroup CVA approach above: quicker to wire up - no NG_VALUE_ACCESSOR/NG_VALIDATORS providers, no writeValue/registerOnChange boilerplate - but it only works inside one Reactive Forms tree. The component isn't a portable, self-contained control anymore: it requires an ancestor <form [formGroup]> to graft onto, can't be dropped into a Template-driven form, and can't be reused standalone the way a true CVA control can. Control Container lookup: formGroupName/formControlName (and ngModelGroup) find their parent by searching up the injector tree for a ControlContainer - any of ngForm, FormGroupDirective, NgModelGroup, FormGroupName or FormArrayName. That ancestor is exactly the instance this slide's viewProviders re-publishes, so the child's controls attach to the host's own form.

Summary

  • Signal Forms are the current standard
  • To create a custom Signal Form Control, implement the appropriate FormValueControl or FormCheckboxControl interface
  • Custom Signal Form Controls are used to encapsulate complex input logic and provide a single [formField] binding
  • Validation is done via schemas within the host not the custom form controls themselves
  • Parsing is the exception, handled internally by custom form controls
  • If a custom field should provide complex validation, it should expose it via a companion schema
  • Signal Forms are compatible with existing Reactive Forms and Template-driven Forms
Closing recap distinguishing what participants must know going forward (Signal Forms) from what still exists in the wild (Reactive Forms/Template-driven Forms).
