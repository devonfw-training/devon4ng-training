Angular Form Types - Detailed Comparison

Template-driven Forms Reactive Forms Signal Forms
Form model HTML template Defined in a component Defined in a component
Data model Unstructured Structured Structured (typed)
Predictability Asynchronous Synchronous Synchronous
Form validation Directives Functions Schema functions
Mutability Mutable Immutable Signals (set / update)

Reactive Forms treat the form model as immutable - a change like setValue replaces the value rather than mutating it in place. Signal Forms keeps that same snapshot semantics, just exposed through signals instead of an AbstractControl tree.

Backup companion: the fuller side-by-side comparison from the legacy deck (form model, data model, predictability, validation style, mutability), extended with a Signal Forms column. Legacy "when to use" guidance, Template-driven Forms vs Reactive Forms: - Template-driven Forms: the template is the source of truth; suited to simple forms (e.g. login / sign-up); two-way binding; harder to test; doesn't scale well - reach for it only when the forms and their logic are simple. - Reactive Forms: the form model is the source of truth; more scalable, reusable and testable; synchronous and immutable. - Signal Forms keeps the model-as-source-of-truth and synchronous predictability, now expressed through signals.

Signal Forms

Manage form state by building on the reactive foundation of signals.

  • Automatic two-way binding
  • Type-safe field access
  • Centralized schema-based validation

Introduced as experimental in Angular 21 - stable since Angular 22.

Introduces Signal Forms as the deck's main topic and previews its three headline benefits before the detailed slides that follow.

Custom Form Fields - Why Talk About This?

  • Manual wiring - works once
  • Breaks when reused elsewhere
  • Own interface = everyone has to learn it
  • Reusable = same interface as native fields
Frames the whole custom-fields discussion: manual wiring works once but doesn't scale, which is why a reusable field must speak Angular's own control interface instead of inventing a new one. - manual wiring: track value yourself, emit changes yourself - works, but only in the one place you built it for - reused in a different form -> breaks down, pattern doesn't carry over - could invent your own interface instead of Angular's - but then every other dev has to learn YOUR interface instead of the standard one - reusable custom field needs to speak the same interface as Angular's native fields (input, select, ...) - for Signal Forms that interface is FormValueControl / FormCheckboxControl, not ControlValueAccessor - see next slides - second half of reusability, beyond the interface: don't bake decisions into the field's implementation (e.g. which format is valid, which values are allowed, when to switch segments) - forward those decision factors as inputs and let the using component decide. Field stays generic, host decides the specifics.

Custom Validators Live in the Schema

Before building a custom field, note where a custom validator lives: in the schema, not in the field. A plain native <input> already gets custom validation:

            
              loginForm = form(this.loginModel, (path) => {
                // custom rule: return an error object, or null when valid
                validate(path.website, ({ value }) => {
                  return value().startsWith('https://')
                    ? null
                    : { kind: 'https', message: 'URL must start with https://' };
                });
              });
            
          
<input [formField]="loginForm.website" />

The field (native here) does nothing - the schema owns the rule. Error shape is always { kind, message? }; all rules run, no short-circuit.

Establishes the baseline rule before discussing custom fields at all: custom validation always lives in the schema, even for a plain native input with no custom component involved. - validate(path, ctx => error | null) is the custom-rule primitive; siblings are validateTree() (subtree / cross-field), validateHttp() (async, drives pending()), validateStandardSchema() (Zod/Valibot) - ctx also carries valueOf()/stateOf()/fieldTreeOf() to reach other fields - that's how cross-field rules work (next slide) - key teaching point: this is identical whether [formField] sits on a native input or a custom component - the control never validates

Reusable & Cross-field Custom Rules

Wrap validate() in a function - now it's used like a built-in:

            
              function requireHttpsUrl(path: SchemaPath<string>, opts?: { message?: string }) {
                validate(path, ({ value }) =>
                  value().startsWith('https://')
                    ? null
                    : { kind: 'httpsUrl', message: opts?.message ?? 'Use https://' });
              }

              form(this.model, (path) => requireHttpsUrl(path.website));

Cross-field rules read another field via valueOf() - and re-run reactively:

            
              validate(path.confirmPassword, ({ value, valueOf }) =>
                value() === valueOf(path.password)
                  ? null
                  : { kind: 'passwordMismatch', message: 'Passwords do not match' });

Conditional? Gate a rule with the when option, or groups of rules with applyWhen().

Shows wrapping validate() in a function makes a rule reusable like a built-in, and that cross-field checks are just another validate() reading a sibling field via valueOf() - not a separate mechanism.

              function requireHttpsUrl(c: AbstractControl): ValidationErrors | null {

              }

              // cross-field: validate the group, not a single control
              function rangeOrder(g: AbstractControl): ValidationErrors | null {
                const { from, to } = g.value;
                return isBefore(from, to) ? null : { rangeOrder: true };
              }

                website: new FormControl('', [requireHttpsUrl]),
                slot: new FormGroup(

                  { validators: [rangeOrder] },

              });

Native Controls: Wired Up by a Function

When [formField] sits on a real <input> / <select> / <textarea>, Signal Forms calls this internally:

          
            export function nativeControlCreate(
              host: ControlDirectiveHost,
              parent: FormField<unknown>,
            ): () => void {
              // ... reads/writes the DOM element's value ...
              host.listenToDom('input', () => parser.setRawValue(undefined));
              host.listenToDom('blur', () => parent.state().markAsTouched());

              parent.registerAsBinding();
              return () => { /* keep the DOM in sync on every field update */ };
            }

No code of yours runs here - this bridge ships with Angular for every native form element.

Illustrates that a native input/select/textarea gets its Signal Forms wiring for free from Angular's nativeControlCreate - exactly the bridge a custom field must replicate via FormValueControl to behave the same way. - Source: @angular/forms/signals/src/directive/control_native.ts, function nativeControlCreate - Simplified: the real implementation also handles value parsing, min/max, <select> option tracking, etc. - Key line for this topic: host.listenToDom('blur', () => parent.state().markAsTouched())

[formField] is a single directive matched by attribute selector - it decides at runtime what it's sitting on:

              export class FormField<T> {

                ɵngControlCreate(host: ControlDirectiveHost): void {
                  if (this.controlValueAccessor) {

Several directives can match the same formControlName/ngModel - Angular picks exactly one value accessor:

Angular Internals: The ControlValueAccessor Interface

            
              interface ControlValueAccessor {
                // model -> view: write a new value into the DOM element

Custom Field + Custom Validators

The field is built - now wire it to validation. Two running examples:

  • app-rating-input - a single FormValueControl<number>: shows how config & constraints flow into the control, and the "no parse step" extreme
  • app-corporate-email-input - has a real parse step: shows internal (parse) vs external (schema) validation, and a companion schema that ships the whole policy

One rule runs through all of it: the control displays validation, the schema performs it.

Transition slide framing the two running examples (rating-input, corporate-email-input) used to explore where validation logic should live. The composite/nested case (time-range picker) gets its own full topic later.

Division of Labour: Schema Validates, Control Displays

            
              // schema owns the rule
              feedbackForm = form(this.model, (path) => {
                min(path.rating, 1, { message: 'Please select a rating' });
              });
            
          
            
              // the control holds NO validation
              export class RatingInput implements FormValueControl<number> {
                value = model(0);
                touch = output<void>();
                maxStars = input(5);
              }
            
          
            
              <app-rating-input [formField]="feedbackForm.rating" />
              @if (feedbackForm.rating().touched() && feedbackForm.rating().invalid()) {
                <p>{{ feedbackForm.rating().errors()[0].message }}</p>
              }

Anti-pattern: an isValid() inside the control. Define rules in the schema; let the control render the result.

Applies the schema-validates/control-displays rule to the rating field specifically, as the positive example to contrast with the CVA anti-pattern backup below. - companion point (previously its own "Config & Constraints Flow Into the Control" slide): besides errors()/invalid() state, two things flow INTO the control, from two different places: - channel 1: maxStars - the control's OWN config input (how many stars to render), passed directly by the host - the "host decides the specifics, field stays generic" narrative from the Why slide - channel 2: [formField] also forwards the schema's constraint VALUES (min/max/required/minLength/maxLength/pattern) down to the control; the control reads them only to enhance the UI (e.g. dim stars below min, mirror to HTML5 attrs), it never runs them to validate - e.g. host template: <app-rating-input [maxStars]="10" [formField]="feedbackForm.rating" /> and in the control: maxStars = input(5); min = input<number>(); - we deliberately keep only min(path.rating, 1) in the schema here - an extra max(..., 10) would be redundant for a star rating (you can't click an 11th star when only 10 are drawn) and the duplicate 10 made maxStars and max look like the same knob - the error channel is one-directional: form -> control. The control's only way to push an error up is a parse error - covered on the error-channel slide

Signal Forms has no NG_VALIDATORS equivalent - see the error-channel slide.

CVA: Host Validators Stack On Top of Internal Ones

The host can add its own validators - they run in addition to the control's internal ones:

            
              // reactive: control self-validates (min 1) + host adds more
              new FormControl('', [Validators.required, maxRating(10)]);
            
          
            
              <!-- template-driven: extra validator directives on the same element -->
              <app-rating-input name="rating" ngModel required maxRating></app-rating-input>
  • NG_VALIDATORS is a multi-provider - Angular composes all of them
  • control.errors is the merged result (collision = same error key wins/overwrites)
  • Add-only: the host can add but not remove the control's baked-in validators

This two-sided validation is exactly what Signal Forms drops - there the control contributes no validators (bar parse errors); all of it lives in the schema.

Backup companion: shows a host can stack its own validators on top of a control's internal ones - a two-sided model Signal Forms drops in favor of the schema owning all rules. Re-validation caveat: this stacking only works because WorkingHours/maxRating are registered as NG_VALIDATORS on the control that's actually part of the parent form tree. If a validator instead lives only inside a child's own internal FormGroup (nested one level deeper, not exposed via NG_VALIDATORS on the component itself), it won't participate in the parent form's validity or submission state - for it to count towards the parent form's validation, it must sit on the top-level control the parent can see, not buried inside the child.

Internal vs External Validation

app-corporate-email-input is a single field, but still has both kinds of checks:

          
            // INTERNAL (control): is this even shaped like an email? A type check, not a business rule.
            // An unparseable raw value becomes a parse error via transformedValue:
            protected readonly rawValue = transformedValue(this.value, {
              parse: (raw) => isValidEmailShape(raw)
                ? { value: raw }
                : { error: { kind: 'parse', message: 'Enter a valid email address' } },
              format: (val) => val ?? '',
            });
          
        
          
            // EXTERNAL (schema): which domain is allowed is a business rule, not a parse - lives in the schema
            validate(path, ({ value }) =>
              value().endsWith('@capgemini.com')
                ? null
                : { kind: 'domain', message: 'Use your @capgemini.com address' });

Parse: can this raw value even become the typed value - the control's job. Validate: is this (already-typed) value allowed - the schema's job. This split holds for every field, flat or composite - see it again on the time-range-picker.

Draws the line between parsing (can this raw value exist - owned by the control) and validation (is it allowed - owned by the schema), now on a field that - unlike the rating - DOES have a parse step. - mirrors the time-picker's hh:mm parse / from<to schema split, now shown on one flat field instead of a composite one - the rating stays the "zero parse, 100% schema" extreme; this field is the "has parse, still splits internal/external" case

The Error Channel Is One-Directional

form → control (inputs)control → form (out)
errors(), invalid() - to displayvalue (model)
touched, disabled, required/min/max/...touch (output, on blur)
parse errors via transformedValue

A control's only way to push an error up is a parse error. There is no Signal Forms equivalent of CVA's NG_VALIDATORS.

The rating has no parse step → zero upward channel → 100% of its validation must live in the schema.

Makes the structural argument explicit: a control can only push a parse error upward, so a general validation rule baked into the component would be invisible to the parent form. - errors / invalid are input() signals - the form pushes them down for the control to render - this is THE structural reason a general validation rule can't live inside the component: it literally cannot reach the field's errors() - the rating makes the point sharpest: no parse => no upward error at all => everything is schema

Reusable Field = Companion Schema

Don't make every host re-type the domain check. Ship a companion schema with the field - here it bundles the whole policy, nothing left for the host to add:

          
            // shipped alongside the control - the domain is intrinsic to this field, not host-configurable
            export const corporateEmailSchema = schema<string>((path) => {
              validate(path, ({ value }) =>
                value().endsWith('@capgemini.com')
                  ? null
                  : { kind: 'domain', message: 'Use your @capgemini.com address' });
            });
          
        
          
            // any host - one line, no re-implementation, nothing to compose on top
            signupForm = form(this.model, (path) => {
              apply(path.workEmail, corporateEmailSchema);
            });

Rule authored once, lives in the schema layer. Contrast with the time-range-picker's companion schema: that one only ships the intrinsic from < to rule - hosts still compose their own business hours on top. Here the policy is complete.

Shows the companion-schema pattern (schema + apply()) as the answer to where a reusable field's intrinsic rule lives, so every host gets it for free instead of re-implementing it - and contrasts a "complete policy" schema (nothing to add) with the time-picker's "intrinsic + host composes more" schema.

Was Co-locating Validation Ever an Anti-pattern?

CVASignal Forms
Self-validating controlNG_VALIDATORS - idiomaticno equivalent; errors is an input
Upward error channelfull validator contributionparse errors only
Home for a rulecontrol or schemaschema (control displays)
Verdictnot an anti-patternco-locating rules → discouraged

Why it shifted: a CVA composite was a black box (parent saw that it was invalid, not why). A Signal field tree is transparent - schema rules aggregate into form().invalid(), attach to a fieldTree, and re-run via valueOf().

Answers directly whether 'schema validates, control displays' contradicts older CVA practice - it's the field's transparency, not a change in taste, that makes schema-only necessary for Signal Forms. - concrete failure if you bake from<to into the component: it can't reach form().invalid(), so the form reports valid with a backwards range and the submit gate lets it through - that is the real anti-pattern - the parse exception stays in the control because a parse failure genuinely is the control's private knowledge

Custom Field Validation - Takeaways

  • The schema validates; the control displays.
  • The only error a control owns is a parse error (transformedValue → {error}). A click-based field like the rating has none → 100% schema.
  • Config & constraints flow into the control (rating maxStars); host decides specifics, field stays generic.
  • Reusable intrinsic rules travel with the field as a companion schema + apply() - not inside the component.
  • CVA self-validation was fine; under Signal Forms it's discouraged because the error channel is form → control only.
  • Composite/nested fields (e.g. a time-range picker) get the same treatment - see Nested Forms.
Recap consolidating the validation-placement discussion into rules participants can apply to their own custom fields.

Summary

  • Signal Forms are the current standard:
    • form model declared in code, reactivity via Signals
    • automatic two-way binding & type-safe field access
    • custom fields implement FormValueControl / FormCheckboxControl - no CVA needed
  • Reactive Forms & Template-driven Forms still exist:
    • see backup slides under "Angular Form Types" for the full recap
    • includes Live Code Examples for both
Closing recap distinguishing what participants must know going forward (Signal Forms) from what still exists in the wild (Reactive Forms/Template-driven Forms).

viewProviders instead of providers: providers cannot reach up to the parent. No CVA, no composite value - just template reuse.

Same technique as the legacy general-info exercise (now in the Exercises section): inject the parent FormGroupDirective in the constructor, addControl its own structure into it, bind via formGroupName/formControlName - just applied directly to the time-range-picker instead of taught abstractly on a generic address field. CVA-only: a Signal Forms composite just binds its children to slices of its own value() - a plain two-way-bindable signal, no ambient form-sharing mechanism needed at all - whereas CVA has no such plain model object and must reach for either a nested FormGroup or this ControlContainer trick. How the sharing actually works: formGroupName/formControlName look up ControlContainer with @Host(), which is restricted to the component's own view, so by default they can't see an ancestor component's FormGroupDirective. The constructor param FormGroupDirective is not @Host()-restricted, so DI walks past the component boundary and injects the real ancestor instance from the host's <form [formGroup]>. viewProviders then re-publishes that same instance as ControlContainer for this component's own view, so formGroupName="slot" inside resolves to it too. Because it's the same object and not a copy, this.form.form.addControl(...) mutates the host's own meetingForm directly - the host's FormGroup starts without a "slot" control at all (e.g. just { room: new FormControl('') }) until the picker adds it. Pro/con vs. the nested-FormGroup CVA approach above: quicker to wire up - no NG_VALUE_ACCESSOR/NG_VALIDATORS providers, no writeValue/registerOnChange boilerplate - but it only works inside one Reactive Forms tree. The component isn't a portable, self-contained control anymore: it requires an ancestor <form [formGroup]> to graft onto, can't be dropped into a Template-driven form, and can't be reused standalone the way a true CVA control can. Control Container lookup: formGroupName/formControlName (and ngModelGroup) find their parent by searching up the injector tree for a ControlContainer - any of ngForm, FormGroupDirective, NgModelGroup, FormGroupName or FormArrayName. That ancestor is exactly the instance this slide's viewProviders re-publishes, so the child's controls attach to the host's own form.

Build an order form whose nested general-info component injects its own fields directly into the parent's FormGroup via ControlContainer.

CVA-only pattern - no Signal Forms equivalent (composite values there are just nested signal slices, see the Time-Range-Picker).

  2. Create order-overview component (ng g c order-overview)
    • This is the parent form - add [formGroup] directive
    • Add apply and cancel buttons
    • On apply show the form (rawValue) in the console
    • Form can be submitted only if it's valid (add a flag submitted)
